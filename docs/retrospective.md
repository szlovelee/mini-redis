# 프로젝트 회고
mini-redis 회고지만 이야기는 mini-react에서 시작해야 할 것 같다. 거기서 느낀 아쉬움이 redis를 진행하는 방식을 바꿨기 때문이다.

### React 때의 나
mini-react는 팀원과 둘이서 일주일 동안 React 없이 Virtual DOM과 Hook을 구현하는 프로젝트였다. 
AI와 개발의 전 과정을 함께해 본 것이 처음이었는데, 가장 재미있었던 건 코드를 짜는 일보다 AI가 일할 수 있는 환경을 만드는 일이었다. 
역할별로 에이전트를 나누고, 각자 어디까지 맡을지, 무엇을 기준으로 판단할지를 가이드로 적어 줬다. 만든 쪽과 검토하는 쪽을 분리하고, 구현 전에 테스트 케이스를 먼저 쓰는 방식도 이때 정했다. 
요구사항 명세를 쓰는 법, 결과를 어떻게 검증할지, 판단의 근거를 어떻게 남길지도 이때 처음 진지하게 공부했다.

진행 순서는 이랬다. 요구사항 명세와 설계를 전체 분량에 대해 먼저 끝내고 검토를 받은 다음 구현으로 넘어갔다. 
문제는 속도였다. AI가 코드를 쓰는 속도가 내 이해 속도보다 훨씬 빨랐고, 이해하지 못한 코드가 부채처럼 쌓였다. 마지막 날에는 쌓인 코드를 이해하느라 밤을 새기도 했다.
그래도 이 경험 덕분에 사람이 중간에서 판단하고 확인하는 human in the loop 방식의 장점이 크게 와닿았다. 
AI가 아무리 빨라도 내가 따라갈 수 있는 속도 안에서 확인하며 가야 한다는 것을 몸으로 배웠다.

### Redis에서의 성장
mini-redis에서 달라진 건 도구나 역할 분담이 아니라 루프 자체였다. react 때는 요구사항과 설계를 전체에 대해 먼저 끝냈다면, 이번에는 큰 틀만 먼저 잡았다. 
첫 단계(iteration 01)에서 범위와 단계 사이에서 공유할 계약만 정하고, 나머지는 단계별로 쪼갰다. 해시 테이블, HTTP API, 만료와 무효화, 동시성, 통합 검증 순서였다. 그리고 각 단계 안에서 다음 순서를 반복했다.
```
요구사항 명세 → 설계 → 검증 → TC 작성 → 검증 → 구현 → 검증 및 테스트
```
짧은 단위로 반복해서 개입하다 보니 이해가 훨씬 빨랐다. 한 단계에서 다룰 요구사항과 설계가 작으니 읽고 판단할 양도 작았고, 구현이 나오기 전에 이미 그 단계의 내용을 알고 있었다. 앞 단계의 실제 결과를 확인한 뒤 다음 단계의 범위를 정하는 것도 가능했다.

react 때부터 해 온 방식은 그대로 유지했다. 구현한 에이전트와 별도로 검토하게 했고, 그 검토에서 결함이 계속 나왔다. 
3단계에서는 캐시 리다이렉트와 숫자 형식을 잘못 허용하는 문제가, 4단계에서는 메모리 할당에 실패하면 항목 수가 어긋나는 문제가, 5단계에서는 완료 통지가 실패하면 요청이 영원히 기다리는 문제가 나왔다. 
고치면 회귀 테스트를 더하고, 고친 범위만 다시 검토받았다.

큰 틀만 먼저 잡았기 때문에 이미 정한 것을 바꿔야 하는 일도 생겼다. 3단계에서 순차 처리로 정했던 서버 구조를 5단계에서 병렬 접수와 단일 명령 스레드로 바꿨는데, 이전 결정을 지우지 않고 새 결정으로 변경 범위를 적어 두었다. 
나중에 "왜 이렇게 됐지?"를 문서만 보고 따라갈 수 있었다.

중요한 판단은 내 몫이었다. 성능 비교에서는 원본 응답에 일부러 지연을 넣지 않고 호출마다 다른 키를 읽게 했는데, 이 비교의 목적이 캐시를 쓰는 이유를 보여 주는 것이었기 때문이다. 
이미 통과한 검증을 전부 반복하지 않고 새로 이어진 부분의 회귀만 고르기로 한 것도 내가 정했다. 해시 버킷을 고르는 방식, 충돌 처리, TTL, 단일 스레드를 쓰는 이유 같은 핵심 로직은 직접 설명해 보며 이해를 확인했다.

### 그래도 남는 아쉬움
그럼에도 코드를 끝까지 책임지고 읽었다고는 말하기 어렵다. 이해하며 따라가기는 좋았지만 모든 코드를 직접 읽은 것은 아니었다. 
더 빠르고 자세하게 따라갈 수 있어야 코드에 대한 책임을 확실하게 질 수 있을 것 같다. 

협업은 지금도 고민 중이다. AI와 함께 개발하다 보니 작업 단위를 나눠 만들고 머지하는 방식이 더 이상 의미가 없다는 생각이 들었다. 
그래서 팀원과 완전히 따로 각자 개발하고 결과를 비교하는 방식을 택했다. 하지만 그렇게 하면 팀으로 일하는 의미를 어디서 찾아야 하는지는 아직 답을 못 찾았다. 

이 두 아쉬움은 이어져 있다고 느낀다. 서로의 코드를 깊이 읽고 리뷰할 기회가 적으면, 내가 읽고 책임질 수 있는 코드의 범위도 좁아지기 때문이다.

### 앞으로
다음에는 각자 구현한 것을 공유하는 자리를 만들고, 리뷰를 지금보다 훨씬 자세하게 해 보고 싶다. 
서로의 구현 의도와 검증 근거를 묻고 답하다 보면, 따로 개발해서 비교하는 방식에서 한 걸음 더 나아갈 수 있지 않을까 기대한다. 이번에 만든 환경과 도구를 바탕으로, AI에게 맡길 일과 내가 직접 판단할 일을 더 분명하게 나누는 것도 다음 목표다.
